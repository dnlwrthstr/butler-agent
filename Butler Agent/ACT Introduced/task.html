Description

In this stage, you'll enhance your assistant by giving it the ability to interact with the real world through tools. You'll implement the ACT part of the THINK-ACT-OBSERVE loop, allowing the agent to execute functions and use their results in the conversation.

The key difference from Stage 1 is that now the assistant can do more than just generate text; it can call functions to retrieve real data. In this stage, you'll add a check_weather() tool that returns actual weather information.

Here's how the enhanced conversation flow works:

User → LLM (THINK) → Tool Call (ACT) → Tool Result (OBSERVE) → LLM (THINK) → Final Response

To enable tool usage, you need to:

  1. Define the tool: Create a tool definition in the OpenAI function calling format, which includes:

    • Type: "function";

    • Name: "check_weather";

    • Description: What the tool does;

    • Parameters: What arguments it accepts (in this case, none).

  2. Implement the tool function: Write the actual Python function that returns weather data;

  3. Register the tool: Create a mapping from tool names to their implementations so you can call them dynamically;

  4. Implement the agent loop: Create a loop that allows the agent to make multiple "thinking" iterations:

    • Call the LLM with tools available;

    • Check if it wants to call a tool;

    • Execute the tool if requested;

    • Add the result back to the conversation;

    • Let the LLM process the result and respond.

When the user asks "What's the weather?", instead of giving a generic response, the agent will:

  1. THINK: Recognize it needs weather data;

  2. ACT: Call the check_weather() tool;

  3. OBSERVE: Receive "Cold, rainy";

  4. THINK: Process the data;

  5. Respond with information based on actual weather data.

Objectives

In this stage, you should:

  1. Define the check_weather tool in the TOOLS_REGISTRY list using OpenAI function calling format.

  2. Implement the check_weather() function that returns "Cold, rainy".

  3. Create a TOOL_NAME_TO_FUNC dictionary to map tool names to their implementations.

  4. Implement the run_agent_loop() function that:

    • Calls the API with the tools parameter

    • Handles both function_call and message response types;

    • Executes tools when requested;

    • Adds tool results back to context;

    • Continues iterating until receiving a final message.

  5. Add logging to show THINK, ACT, and OBSERVE phases.

Example
[USER]: What's the weather like today?
[ENTERING AGENT LOOP]
[THINK]: Model decided to return these items: ['ResponseFunctionToolCall']
[ACT]: Calling "check_weather" with arguments {}
[OBSERVE]: Result Cold, rainy
[THINK]: Model decided to return these items: ['ResponseOutputMessage']
[EXITING AGENT LOOP]
[ASSISTANT]: Today the weather is cold and rainy. Make sure to dress warmly and consider a waterproof jacket!
Key concepts

  • Tools/Functions: Reusable capabilities that the LLM can invoke to interact with external systems or perform specific actions.

  • Function Calling: OpenAI's feature that allows the LLM to request tool execution.

  • Agent Loop: An iterative process where the agent can THINK multiple times, calling tools as needed.

  • THINK-ACT-OBSERVE: The reasoning loop:

    • THINK: LLM decides what to do (call a tool or respond with text).

    • ACT: Execute the tool function.

    • OBSERVE: Add the tool result to context so LLM can see it.

  • Context Management: Keeping track of all messages, tool calls, and tool results in the conversation history.

  • Iteration Limit: A maximum number of iterations to prevent infinite loops (MAX_ITERATIONS = 5).

Tool definition format
{
    "type": "function",
    "name": "tool_name",
    "description": "What the tool does",
    "parameters": {
        "type": "object",
        "properties": {
            # parameter definitions
        },
        "required": []  # list of required parameters
    }
}
Tips

  • The response.output is a list that can contain multiple items.

  • Check item.type to determine if it's a "function_call" or "message".

  • For function calls, item.name contains the function name and item.arguments contains the JSON-encoded arguments.

  • Use json.loads() to parse the arguments string.

  • The call_id from the function call must be included in the function result.

  • Tool results use the format: {"type": "function_call_output", "call_id": "...", "output": "..."}.

  • The loop continues until the LLM returns a message (not a function call).
